# 原生状态页与降智检测设计

- 项目：new-api
- 文档状态：方案已确认，首轮实现已落地；自动规则判定及部署验收尚未完成。
- 日期：2026-10-27
- 本轮交付：检测核心、原生状态页、管理工作台及可选截图服务代码与本地回归测试；未部署、未启动真实检测、未产生上游模型调用费用。
- 实施边界与启用步骤：见 [实施与部署说明](quality-detection-rollout.md)。以下章节保留完整目标设计，不代表所有验收项均已完成。

## 1. 核心方案

以 new-api 自己的渠道、分组和检测记录替换 Uptime Kuma 数据源，保留 `/status` 访问地址。公开页以**分组为主行**，管理员后台新增独立的“降智检测”菜单。

最重要的约束是：**展示按分组，执行按渠道；同一轮中，一个渠道只生成一次 HTML。**

例如渠道 A 同时属于“标准”“高速”“会员”三个分组：

- 本轮只为 A 创建一条检测记录，向 A 发起一次模型生成请求。
- 生成的 HTML、缩略图、执行耗时和检测结论只保存一份。
- 三个分组引用同一个检测结果，而不是分别运行检测。
- 全站检测次数和费用只计一次；三个分组内都可以展示该结果。
- 某个分组包含多个渠道时，展示该组的覆盖情况，并允许展开查看各渠道样本，不能拿一张图代表整个分组全部正常。

关于是否需要启动 Codex：参考项目的降智工作台使用的是 **Go 后台任务直接调用模型 API，再展示模型返回的 HTML**，不是在服务器启动 Codex CLI 来写文件。这里采用相同的单次生成思路；定时调度则复用 new-api 已有的数据库租约任务框架。

“降智检测”是菜单名称，实际结果区分“生成成功”“规则通过”“待人工复核”“疑似质量下降”等含义。单个 HTML 样本不能证明模型真实身份或整体智力水平。

## 2. 已核对的现状

### 2.1 new-api

1. `/status` 当前调用 `/api/uptime/status`，后端请求外部 Uptime Kuma 的状态页与心跳接口。页面中的分组来自 Kuma 配置，不是本项目的渠道分组。
2. 渠道的 `Group` 是多分组字段，`Channel.GetGroups()` 已提供读取方法；`Ability` 将分组、模型、渠道展开为能力关系。这个展开关系适合查询展示资格，不适合直接生成检测任务。
3. 已有 `SystemTask`、`SystemTaskLock` 和 `ScheduledSystemTaskHandler`，支持周期调度、运行记录、跨主节点租约互斥、续租与失锁取消。
4. 现有任务互斥粒度是任务类型，不是渠道。新增一个“降智检测批次”类型，在批次内部执行去重后的渠道列表，比给每个渠道创建同类型系统任务更符合当前框架。
5. `controller/channel-test.go` 已覆盖指定渠道、模型映射、渠道参数与请求头覆盖、上游适配器调用，可作为执行链路参考。但当前测试请求固定、返回结构主要表达成功或失败，并不是可直接复用的 HTML 检测服务。
6. `pkg/perf_metrics` 已保存“模型 + 实际使用分组 + 时间桶”的请求量、成功量、耗时、首响应耗时和输出速度计数。它没有渠道维度，也没有 P95 所需的分布数据。
7. 当前性能查询合并数据库与本进程尚未落库的计数，不能直接视为多节点实时总量。第一版公开状态页读取已落库的完整时间桶，并明确统计截止时间。
8. Uptime Kuma 还关联控制台概览面板、顶部导航显示开关、系统设置、`/api/status` 返回字段和 OpenAPI 文档，替换时必须一起处理。

### 2.2 codex2api 降智工作台

当前环境中的参考源码位于 `D:/codex2api`，而不是 Windows 用户主目录下的 `~/codex2api`。

已核对的执行流程：

1. 管理员选择账号、模型、思考强度、提示词和超时，提交任务。
2. 后端校验参数，先保存任务，再交由后台执行；HTTP 接口返回 `202 Accepted`。
3. 后台复用账号测试链路，直接向所选账号对应的上游发送请求，不通过其他账号兜底。
4. 请求附带“完整、自包含 HTML；SVG/CSS/JavaScript 内联；不引用外部资源”的统一要求。
5. Responses 类和 Claude 类使用各自请求格式。Codex 的长生成检测明确使用独立 HTTP 流，不依赖 WebSocket 续链。
6. 后端收集内容、首段输出时间、用量、返回模型与终态，持续保存进度；页面轮询列表和详情。关闭页面只取消轮询，不终止任务。
7. 输出提取、HTML 预览和 SVG 导出有单独实现；这不等于已经有通用的服务端网页截图或可靠的自动“智力评分”。
8. 存在对“尚无输出时发生流中断”的有限重试。本方案第一版不沿用生成重试，优先满足一次渠道生成与费用可控的要求。
9. 复用的连通性测试还可能写入账号错误/冷却状态，或在成功后清除失败状态；参考实现不是纯观察路径。本方案只借鉴必要的请求执行能力，不照搬这些影响生产路由的副作用。

值得借鉴：后台任务持久化、指定目标、不依赖页面存活、提示词快照、流式输出上限、取消与超时、隔离预览。

不直接照搬：账号体系、供应商专用传输逻辑、参考项目的视觉样式、前端整页实现，以及将任意生成成功视为“未降智”的判断。

## 3. 第一版范围

### 包含

- 原生 `/status`，分组列表、状态筛选、时间窗口、趋势、检测覆盖和生成结果预览。
- 后台“降智检测”：检测概览、渠道配置、提示词预设、任务记录和运行设置。
- 全局检测间隔、每渠道一个检测模型与一个提示词、手动运行、取消、并发和预算限制。
- 按渠道去重的持久化任务与历史结果。
- HTML 保存、基础规则检查、隔离截图、基线样本与人工复核。
- 分组公开白名单、公开别名及渠道样本公开控制。
- 控制台原 Uptime 面板切换到新数据源。

### 暂不包含

- 启动 Codex CLI、执行模型生成的终端命令、安装生成项目依赖。
- 同一渠道每轮遍历全部模型或全部提示词；这会直接违反“一个渠道一次”的默认要求。
- 额外调用另一个模型进行评分；这会增加成本，也需要单独校准评审可靠性。
- 用单个样本识别模型真假，或因为一次图画不好就自动封禁渠道。
- 将历史平均耗时冒充 P95，将没有数据的时间段补成正常。
- 完整替换现有渠道可用性测试、自动禁用与恢复机制。

## 4. 公开状态页的信息结构

### 4.1 页面对象与入口

访问者主要关心“我选的分组现在是否可用、速度怎样、近期生成质量是否稳定”。主列表一行对应一个真实渠道分组，不把渠道列表仅仅改名成“分组列表”。

- 保留公共布局、站点标识、主题切换、语言切换和 `/status` 地址。
- 默认显示管理员明确发布的分组；未发布的内部组、测试组不能从接口、搜索选项或缩略图地址泄漏。
- `auto` 这类自动路由选择项不自动当作一个真实渠道分组，不为它额外创建检测。
- 公开可见与用户是否有权限调用某个分组是两回事：状态页只展示公开信息，API 调用权限继续由现有认证与分组授权决定。

### 4.2 从上到下的布局

**页头**：标题“服务状态”，一行说明，以及“指标统计截至”“最近检测完成”两个独立时间。刷新按钮只刷新已保存数据。

**摘要条**：公开分组数、存在异常的分组数、近期已检测的独立渠道数。采用轻量横向摘要，避免四五张大号仪表卡占满首屏。全站渠道数按唯一渠道去重，不能对分组数字直接求和。

**筛选区**：分组搜索、模型筛选、状态筛选，以及 1h / 6h / 24h / 7d 时间窗口。模型筛选依据实际模型元数据与能力关系，不用渠道类型猜测模型厂商。第一版优先精确模型筛选，厂商品牌页签后续再扩展。

**主列表**：建议按以下顺序展示信息。

1. 分组名称、简短说明、公开渠道数量。
2. 当前状态与检测覆盖，例如“规则通过 2 / 3，1 个待检测”。
3. 真实请求成功率、平均耗时、输出速度；列标题明确这是业务流量指标。
4. 一条当前选定指标的趋势线，默认成功率；不要在同一小图混画毫秒和百分比。
5. 最近质量检测结论、检测模型、时间，以及可点击的 HTML 渲染缩略图。
6. 查看详情操作。

分组倍率可作为次要信息。只有选中具体模型且价格含义明确时，才展示对应输入/输出价格；复用现有价格展示逻辑。表达式定价显示“动态计费”，不能由分组倍率推导一个虚假的统一单价。

**分组详情**：桌面右侧抽屉，手机全屏面板。展示业务指标趋势、所含公开渠道的检测结果、样本覆盖、最近失败原因分类和历史样本。渠道名称使用公开别名，不展示上游地址、内部备注或密钥。

### 4.3 一个分组有多个渠道时

- 公共行展示分组整体的业务指标；每个渠道的生成检测单独列在详情中。
- 缩略图优先选择最新的待复核/异常样本；没有异常时选最近有效样本。标注“样本 1 / N”，而不是用唯一缩略图暗示全组结果一致。
- 多个分组引用同一渠道时，复用相同 `run_id` 和 `artifact_id`，可注明“共享检测样本”。
- 检测仅覆盖已配置的代表模型。选择其他模型后，没有对应样本就显示“该模型未检测”，不能把一个模型的结果复制成所有模型均通过。
- 首屏响应不返回原始 HTML；详情打开后再获取截图和必要的检测明细。

## 5. UI 方向：借鉴 Arc UI，而不是复制参考截图

已查看 `uiarc.dev` 首页、按钮与可排序表格页面，并阅读 Tabs、Sortable data table、Sparkline 的公开组件说明。

### 5.1 采用的设计特征

- 中性底色、细边界、圆角容器和清楚的字号层级。
- 控件有明确主次：一个主要操作，其他操作使用低强调按钮。
- 筛选与内容靠近，数字整齐对齐，状态通过文字、图标和少量颜色共同表达。
- 页签选中指示、按钮等待反馈、详情面板过渡采用轻量动效。
- 保留充分行距和可点击面积，而不是密集小字、荧光边框和大量圆环。

Arc 首页的彩色光晕与大面积宣传区不搬进状态页。这里借鉴它的组件质感与层级，而不是把监控页面做成宣传页。

### 5.2 视觉规格建议

以下是草案色板，不是要求修改全站主题：

- 浅色页面底色 `#F7F7F8`，内容面 `#FFFFFF`。
- 主文字 `#24262B`，结构边界 `#E7E8EC`。
- 主操作强调色 `#3F5BD9`，成功语义参考 `#16805D`。
- 深色使用中性炭灰底与略亮内容面；实际接入现有主题变量，不强制所有用户切换主题。
- 警告与错误继续用项目语义颜色变量，不给不同厂商、分组各配一种高饱和色。

字体上，参考站使用 Geist / Inter 的无衬线层级；项目优先沿用已有的 Public Sans、Space Grotesk 与中文系统字体回退，不为模仿外观增加远程字体依赖。表格数字使用等宽数字特性。

尺寸建议：

- 内容最大宽度约 1360–1440px；桌面侧边距 32px，手机 16px。
- 标题 32px 左右，手机 26–28px；正文/表格 14px，辅助文字 12–13px。
- 列表行高约 88–104px，缩略图约 112 × 64px，完整图片在详情查看。
- 容器圆角 14–18px，筛选控件圆角 8–10px；主要依靠留白与边界分层，不使用强阴影。
- 交互动效约 120–180ms；尊重减少动态效果设置。自动刷新不重排用户正在阅读的行，不重播全部图表动画。

### 5.3 响应式与可访问性

- 桌面使用结构清楚的表格；中等宽度隐藏次要指标；手机改为两层信息卡，而不是整页横向滚动。
- 长分组名截断但保留可访问的完整名称；空值显示“暂无样本”，不显示 `0%`。
- 图表要有指标名、单位、时间范围和可读文本摘要；细节图支持键盘查看数据点。
- 排序、筛选、抽屉关闭、预览按钮均可键盘操作，关闭抽屉后焦点回到触发按钮。
- 加载、刷新失败、无公开分组、未检测、已过期、渲染不可用分别设计，不用同一个空白面板代替。

实现继续使用项目已有 Base UI、TanStack Table、Tailwind 和图表能力。Arc 的部分组件依赖 Radix，不直接批量安装覆盖现有组件；只借鉴公开交互与视觉原则，若实际引入源码则单独核对许可证，不依赖 Pro 组件。

## 6. 后台“降智检测”菜单

放在管理员导航的“渠道”附近，建议路径 `/quality-detection`。仅管理员及以上可访问，前端路由和后端接口都鉴权，菜单隐藏不能代替接口权限。

### 6.1 检测概览

- 调度开关、运行中的批次、上次完成与下次预计启动时间。
- 已配置渠道数、待检测数、待复核数、预算剩余量、渲染服务状态。
- “立即检测”支持选择渠道或按分组筛选渠道。确认框同时展示“涉及分组数”和“去重后渠道数”，明确实际模型请求上限。
- 有批次运行时显示“查看运行中检测”；不允许通过连续点击另起重叠批次。

### 6.2 渠道配置

每个渠道只有一份有效检测配置：是否参与、检测模型、请求协议、预设提示词及版本、可选思考强度、超时覆盖、公开别名、样本是否公开。

- 模型优先使用明确的检测配置；首次设置时可推荐渠道现有 `TestModel`，但必须检查它确实支持文本生成。
- 不默默回退到“模型列表第一个”或一个固定模型。
- 多密钥渠道一次只抽取一个当前可用密钥；它是抽样，不代表所有密钥都健康。密钥序号仅管理员可见，密钥值永不进入任务记录。
- 分组只影响筛选与展示，不提供“同一渠道在不同组使用不同检测提示词”的第一版配置。
- 图片、音频、视频、Embedding 等不支持 HTML 文本生成的目标显示“不支持此检测”，不计为失败。

### 6.3 提示词预设

支持内置预设、自定义预设、复制、编辑、归档和设为默认。每次修改形成不可变版本，历史任务保存完整提示词快照，旧样本不会随编辑发生变化。

建议内置两类预设：

1. **视觉比较**：SVG 动物骑自行车、时钟、齿轮等，主要用于图片比较和人工复核，不仅凭“含有 SVG”判断质量通过。
2. **可验证页面任务**：明确要求若干可识别元素和简单交互，例如按钮切换指定文本。随预设提供受信任、版本化的检查规则，用于稳定验证是否遵守指令。

一次任务只采用一个预设，不自动把预设库全部跑完。自定义提示词默认只做通用输出检查与人工复核；不允许管理员输入任意服务器脚本作为评分器。

模型输入由“统一 HTML 输出要求 + 预设正文”组成。统一要求包括单文件、内联资源、不访问外部网络、只输出 HTML。保存合成输入和参数指纹，以便比较同一条件下的样本。

### 6.4 运行记录

按批次、渠道、模型、预设版本、时间和结果筛选。详情展示生成文本、截图、命中/未通过的规则、使用量、耗时、终止原因、配置版本，以及与已确认基线的并排比较。

“设为基线”和“人工复核”记录操作者、时间与备注；不覆盖原始输出或原始规则结果。仅相同模型、预设版本、关键参数与渲染版本的结果自动列为可比较。

### 6.5 建议默认值

这些是实施建议值，不是参考项目现有参数：

- 定时检测默认关闭，配置目标与预算后由管理员启用。
- 全局间隔默认 60 分钟，可配置 5 分钟到 7 天。
- 间隔定义为“上一批次结束后，到下一批次启动的最短间隔”，遵循现有调度器语义；手动批次完成也更新这一间隔。
- 并发默认 3，配置上限建议 10；单渠道同一时间只有一个生成请求。
- 单渠道超时默认 10 分钟，可配置 1–30 分钟。
- 提示词上限建议 16,000 UTF-8 字节；输出文本上限 1 MiB。
- 输出 token 上限默认建议 8,192，按模型能力校验，并受项目统一的 max-tokens 上限约束；只有协议支持时才发送对应字段。
- 自动生成重试次数为 0；手动重测是一个新批次并单独计量。
- 每日生成调用上限建议 500，同时配置每日预留 token 预算；UTC 日界统计，在界面明确说明。
- 检测元数据保留 90 天，原始输出与截图默认 14 天；被设为基线的样本单独保留，但有数量/容量上限。

## 7. 调度与按渠道去重

### 7.1 任务结构

新增 `quality_detection` 系统任务类型，一个 `SystemTask` 对应一个检测批次；批次下包含多条渠道检测记录。

调度器只决定何时启动；服务层负责目标快照、持久化、预算与并发执行。手动运行与定时运行走同一条入队逻辑。

一轮处理过程：

1. 读取启用的渠道检测配置；若管理员通过分组选目标，先解析为渠道 ID 集合。
2. 按渠道 ID 去重，过滤不支持的目标，固定每个渠道的模型、提示词版本与参数。
3. 创建批次与全部渠道记录，保存当时的分组关联和配置指纹。此时尚未调用模型。
4. 由数据库原子操作预留本轮调用次数与 token 预算；预算不足时不启动这轮生成，给出明确原因。
5. 按并发上限领取 `queued` 记录，原子变为 `running`；成功取得记录的执行者才有调用权限。
6. 每条记录最多发起一次生成，流式收集文本与用量并完成终态落库。
7. 后续规则检查、截图和发布只消费已保存输出；截图重试不重新调用模型。
8. 查询层将同一渠道结果关联到各个符合展示条件的分组，生成公开页面数据。

### 7.2 去重与幂等约束

- 渠道检测记录唯一键为 `(batch_id, channel_id)`，不含分组。
- 一个渠道第一版只有一份启用的配置；不能因模型/提示词列表的笛卡尔积产生额外调用。
- `SystemTask` 的活动任务唯一约束和租约负责跨实例批次互斥；不能只用内存互斥或 Redis 锁作为唯一保证。
- 手动提交携带请求幂等键。同一键、相同请求返回已有批次；同一键不同参数返回冲突。
- 另一批次正在运行时，新请求返回 `409` 和当前批次标识，不把新选择静默丢弃或追加到已经冻结的目标列表。
- 定时触发碰上正在执行的批次就跳过，不积压每个错过的时间点。
- 模型适配器中的自动重试、跨渠道兜底和生成请求重放也必须禁用；正常的调用前凭据刷新不算模型生成。

这里保证的是同一逻辑检测不因分组展开、重复提交、并发领取或重试而重复发起生成。网络中断后无法证明上游是否已经执行，因此不宣称远端“严格恰好一次”。发送后结果不明时记录中断，等待下一轮或管理员明确重测，不自动重放。

### 7.3 取消、失锁和重启

- 页面关闭不取消任务；管理员的“停止批次”写入持久化取消标记。
- 执行者观察取消标记，停止领取排队任务，并通过 Context 取消正在运行的请求；已产生费用无法撤销。
- 失去数据库租约时立即取消执行，禁止旧执行者继续提交最新结果；渠道结果写入同样校验批次所有权，不能只保护父任务终态。
- 重启后 `running` 且失去所有者的记录标为 `interrupted`，不重新生成。未明确完成的预算预留保守保留，避免不明用量造成预算绕过。
- 后续轮次可正常检测同一渠道，但必须有新的批次 ID。失锁清理、子任务终态和预算清理需要联动，不能只依赖现有父任务过期处理。
- 当前系统任务仅有 pending/running/succeeded/failed 四种状态。取消、预算阻止、部分完成等业务结果放在质量批次状态中；公共系统任务面板需要显示可理解的结果摘要。

## 8. 模型执行与计量

### 8.1 复用边界

执行时固定渠道 ID，复用现有渠道凭据选择、模型映射、请求头/参数覆盖和提供商适配器，不能向普通公开路由提交请求后任由网关重新分配渠道。

现有 `controller/channel-test.go` 可借鉴，但需要提炼可接收自定义请求、输出事件接收器与取消上下文的稳定执行接口。不能直接复用固定问候词测试，也不能把整段检测逻辑复制成第二套不一致的转发实现。

复用时须显式区分“执行一次请求”和“将测试结果应用到生产路由状态”。第一版质量检测不得通过共享测试回调自动禁用/恢复渠道、修改路由权重或清除既有失败/冷却状态；原有连通性测试策略保持不变。凭据刷新和既有请求限制仍按现有规则处理，不因内部检测标记获得绕过权限。

依赖方向需要注意：`relay` 已依赖 `service`，`service` 不应反向直接导入 `relay`。建议在服务层定义检测执行器接口，由能够组合渠道上下文和转发适配器的适配层实现，在启动时注入，参考现有异步任务适配器注册方式。

### 8.2 请求与结果

- 支持第一版明确验证过的文本协议：Chat Completions、Responses、Claude Messages；其他适配器按能力逐步接入，不以“支持 40+ 渠道”等同于所有渠道都能立即运行此检测。
- 保留渠道本来会应用的模型映射与参数覆盖，并记录实际参数指纹；覆盖导致提示词、模型或预算约束失效时，应报配置冲突而不是悄悄测试另一个条件。
- 检测使用固定的内部测试上下文，不随着展示分组而切换上下文。依赖用户/分组的参数覆盖可能令实际业务行为不同，界面明确本功能检查的是渠道代表请求，不是每个分组完整的授权与计费路径。
- 后端保存原始请求模型、映射后的模型和上游自报模型；上游自报模型不是身份认证证据，公开页默认只展示配置的检测模型。
- 使用有上限的流式接收器，不使用无限累积的响应缓冲。分别记录首次可见文本、生成结束、完整任务结束。
- 流必须有正常完成证据；HTTP 200、收到若干 token 或提前关闭连接，都不能直接计为生成完成。
- 可选标量参数使用指针和 `omitempty`，区分未传与明确的 0/false。所有 JSON 编解码使用 `common` 封装。

### 8.3 成本归属

检测是站点运维支出：上游仍可能收费，但不扣普通用户钱包或订阅额度，不伪装成普通用户请求混入业务成功率、排行榜与用量统计。

新增明确的内部用途标记，只能由服务端设置，外部请求不能通过字段或请求头获得免计费资格。检测记录单独保存实际/估算 token、调用次数、预算预留与结算状态。

- 没有用量信息时展示“用量未知”，不是 0；中断任务不能无条件退回全部预留。
- 执行前预留预算，完成后按可信用量结算。跨日任务计入预留时的 UTC 日期，避免跨日重复放行。
- 如显示金额，必须区分“按本站定价估算”和“真实上游成本”；缺少上游成本配置时不宣称精确费用。
- 如接入现有配额/价格计算，遵循 `pkg/billingexpr/expr.md` 与统一 `common` 饱和转换、异常审计约束，不复制旧测试代码中的裸数值转换。
- 正式实现必须验证预留、成功、取消、超时、失锁、输出超限和用量缺失路径，确保既不产生负扣费，也不误扣用户资金。

## 9. 质量判断与状态语义

### 9.1 三个状态分开保存

**执行状态**：queued、running、completed、failed、cancelled、interrupted、skipped。回答任务是否跑完。

**质量结果**：not_evaluated、rules_passed、needs_review、suspected_degradation。回答样本是否满足当前版本的规则、是否需要人看。

**新鲜度/可用性**：fresh、stale、unknown、paused，以及上游请求成功/失败事实。回答结果是否近期有效、是否存在可达性异常。

示例：模型请求成功但生成了不完整页面，应是“执行完成、输出异常待复核”，而不是“上游宕机”。截图服务故障应是“渲染不可用”，不是“模型降智”。

### 9.2 第一版的判断依据

1. 检查是否有可提取的 HTML、大小是否合规、是否截断、是否引用被禁止的外部资源。
2. 在隔离渲染环境中检查文档能否呈现、是否存在未处理错误；这些只证明基本有效性，不证明画得好。
3. 对有明确检查规则的内置预设，验证约定元素和交互。规则必须与提示词一致，不能要求模型满足提示词没有要求的 DOM 结构。
4. 对开放式绘图与自定义预设，默认给出“已生成，待人工复核”，提供基线与当前样本的并排查看。
5. 同一比较条件下，已有确认基线且连续两轮违反相同关键规则，可标记“疑似质量下降”；两轮都是正常计划轮次，不额外调用模型确认。
6. 没有基线、模型/预设/参数变化、渲染环境变化或上游请求失败时，不套用该降级判断。人工复核结论另行显示来源与时间。

第一版不输出看似精确但未经校准的“智力 96 分”。规则通过也不显示成“保证未降智”，更不自动改变渠道路由权重或封禁状态。

### 9.3 分组汇总

- “规则通过”：所有应展示的已配置目标都有近期对应样本，且其适用规则通过；另列未配置/不支持目标，避免把部分覆盖说成全覆盖。
- “待复核”：存在开放式样本未复核、规则未通过或疑似下降；展示具体数量。
- “部分不可用”：近期渠道检测有明确上游失败，同时仍有成功样本。它是检测观察，不是对每次业务路由结果的保证。
- “检测请求全部失败”：完整覆盖的近期样本都发生上游失败；不直接表述为所有模型全站宕机。
- “数据不足/已过期”：未覆盖、缺少近期结果或配置已变更；不能用旧成功样本继续显示全绿。
- 全局暂停检测后显示“检测已暂停”，保留历史时间，不自动把历史标成当前正常。

新鲜度建议阈值为两倍配置间隔加最大单次执行时间及调度容差。接口返回 `stale_after`，前端依据服务端时间判断，不能用浏览器最近请求成功的时间冒充最近检测时间。

## 10. 指标来源与统计口径

页面明确区分两类数据：**业务请求指标**和**定时检测指标**，不把它们混成一个成功率。

### 10.1 业务请求指标

来源为既有 `perf_metrics` 的原始累计计数。新增按公开分组批量聚合的查询，避免前端对每个组、每个模型逐一请求。

- 成功率 = 成功请求总数 / 请求总数。
- 平均耗时 = 累计请求耗时 / 请求总数。
- 首响应耗时仅对有该计时的流式样本计算，并沿用现有指标语义；不能直接称为新的“首次可见文本时间”。
- 输出速度 = 累计有效输出 token / 对应生成秒数。
- 多模型汇总用累计计数加权，不能平均已有百分比或平均速度。默认模型选择为全部时标明“跨模型汇总”，选择具体模型后才适合横向比较。
- 当前存储没有渠道 ID，不能反推某个渠道的业务成功率；渠道详情只展示新采集的渠道检测指标。
- 第一版没有 P95；将来若需要，增加直方图或合适的分布聚合，不从平均数估算。

第一版使用数据库已完成时间桶，统一读取一致的闭合窗口，返回 `window_start`、`window_end`、`bucket_seconds` 和 `data_until`。默认现有时间桶为一小时，页面应显示“截至整点的统计”，不能标榜秒级实时。需要更实时的多实例数据时再单独完善全局活动桶归属与去重。

公开页面默认不暴露真实业务精确请求量；后端仍保留计数用于正确加权与样本量判断。可返回“样本不足”标记，管理员详情可查看完整计数。

### 10.2 检测指标

来源为真实渠道运行记录：请求是否完整完成、首次可见文本耗时、生成时长、使用量、规则结果与样本时间。

- 检测成功率只以实际发起的生成请求为分母；排队、取消前未发起、不支持、预算阻止、渲染失败不伪装成上游失败。
- 发起后超时、流中断等保留明确分类；人工取消单列，不用于判断渠道质量下降。
- 某渠道在多个组显示时，组内可引用它一次；全站统计按唯一 `run_id` 去重，不能累加各组比例。
- 缺少 usage 或无法区分推理 token 与可见输出 token 时，速度显示不可用或清楚标注估算，不能混用不同 token 语义作精确排名。
- 无记录的时间桶为 `null`；曲线断开，不填 0、不填 100、不按总体成功率伪造历史形状。
- 用户手动样本可出现在最近结果与历史中，但趋势/降级判断默认按计划轮次计算，防止反复手动重测改变统计含义。

## 11. HTML 产物与渲染

### 11.1 产物只生成一次

保存原始模型文本、提取后的 HTML、内容哈希、提取器版本、规则版本、渲染版本和截图。提取失败保留原始文本供管理员查看，不擅自补写代码后声称模型已经完成。

截图使用固定视口、字体、语言、时区和捕获策略。动画可保存固定采样时间的少量帧，辅助观察；帧差只能说明画面变化，不能证明自行车动作正确。截图处理不再次调用模型。

### 11.2 渲染部署

推荐新增独立的受限渲染进程/容器，使用维护中的浏览器自动化工具生成 PNG/WebP。Go 网关本体不承担任意网页执行，不需要安装 Codex CLI。

渲染端只接受已限制大小的 HTML 与受信任的渲染参数，不接受用户提交任意 URL。浏览器进程无站点密钥、无主服务数据库凭据、无宿主目录挂载，关闭外网及内网访问，限制 CPU、内存、运行时间和输出大小，保留浏览器沙箱。

没有配置渲染服务时，模型生成与输出保存仍可工作，但界面明确“缩略图未生成/渲染不可用”，不伪装成模型失败。要完整实现参考图中的结果缩略图列，部署验收必须包含可用的渲染服务。

### 11.3 展示与隔离

- 公共列表与详情默认只展示已生成的 PNG/WebP，不执行模型输出的 HTML/SVG 脚本。
- 管理员第一版默认看截图、纯文本源码和下载文件。HTML 下载使用附件响应，不能以内联可执行文档形式暴露在管理后台同源地址。
- 后续若增加交互预览，应使用独立预览域、严格内容安全策略和不带同源权限的 iframe 沙箱；避免将输出通过 `dangerouslySetInnerHTML` 注入主站。内容安全策略不能替代服务端浏览器的网络与进程隔离。
- 图片与输出通过受控产物 ID 读取，不能把文件系统路径或对象存储凭据交给客户端。
- 公共截图的每次读取都校验当前公开权限，缓存时间有限；撤回公开权限同时失效缓存。公开 API 永不返回提示词全文、原始上游错误、密钥或内部渠道信息。

### 11.4 存储与保留

元数据存主数据库，较大的输出与图片存专用产物存储。单实例可使用配置目录，多实例必须使用共享存储或对象存储，不能把一台机器的本地路径当作所有节点可读的 URL。

避免直接把 1 MiB 输出塞入 MySQL 普通 TEXT 列；第一版使用外部产物存储解决大字段与多数据库兼容问题。先写不可变产物，再提交引用元数据；定时回收未引用对象与过期产物。清理时保护当前基线和有效最新样本，不产生仍被页面引用的失效图片。

## 12. 数据模型建议

以下为新增模型建议，字段名可在实施时按现有风格调整。

### 全局设置

使用独立设置域保存调度开关、间隔、并发、超时、输出限制、预算、保留天数，以及状态页开关、公开分组和公开别名。公开设置与执行设置分离，发布一个分组不等于启用付费检测。

### `QualityPromptVersion`

预设标识、版本、名称、正文、规则类型与版本、归档状态、创建者与时间。唯一约束为预设标识加版本；历史版本不可变。

### `ChannelQualityProfile`

渠道 ID 唯一；检测开关、检测模型、协议、预设版本、思考参数、超时覆盖、公开别名与样本公开开关、配置版本。分组关系仍以现有渠道/能力关系为准，不再建立另一套可独立编辑的渠道分组。

### `QualityProbeBatch`

关联唯一 `SystemTask`，保存触发方式、操作者、请求幂等键、请求指纹、配置版本、目标数、取消标记、业务终态与摘要。用于持久化取消和批次契约，避免把所有控制状态塞进易被进度覆盖的通用任务 JSON。

### `QualityProbeRun`

保存批次 ID、渠道 ID、渠道配置指纹、请求/映射模型、预设与参数快照、执行状态、质量结果、时间戳、错误分类、用量、预算结算状态、产物关联、基线关联与人工复核信息。

唯一约束 `(batch_id, channel_id)`；主要查询索引为渠道加时间、批次、状态。执行记录与产物生成状态分开，截图失败不覆盖模型请求结果。

### `QualityProbeRunGroup`

保存 `(run_id, group_name)` 唯一关系，记录检测当时的真实分组归属。历史查询不依赖数据库专有 JSON 运算。

当前公开页要求该结果既属于当时的分组，又符合当前分组/渠道公开规则。渠道移到新组后不把旧结果伪装成新组历史；下一轮自然产生新关联。配置发生变化的旧样本可以查看，但不能当成当前配置的有效检测。

### `QualityProbeArtifact`

运行 ID、产物类型、内容哈希、大小、私有存储键、提取/渲染版本、状态、创建与过期时间。所有展示分组引用相同产物记录。

### `QualityProbeDailyBudget`

UTC 日期唯一；已预留/已结算调用数和 token 上限，使用事务与条件更新保证原子预留。多数据库使用 GORM；需要行锁时使用 `lockForUpdate(tx)`，SQLite 下另以条件更新结果判定是否成功，不能依赖不存在的行锁语义。

所有结构化快照使用 TEXT 和 `common` JSON 封装；时间用统一 UTC 时间戳。支持 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+，避免新增依赖数据库专有 JSON 类型、部分索引或布尔默认值差异的实现。

## 13. API 契约草案

### 公共只读接口

- `GET /api/status-page`：分组分页列表、摘要、筛选选项、时间窗口与数据新鲜度。
- `GET /api/status-page/groups/:public_id`：一个公开分组的趋势和公开渠道样本。
- `GET /api/status-page/artifacts/:artifact_id/thumbnail`：经过当前公开权限校验的静态截图。

页面主请求包含 `hours`、`model`、`group`、`state`、`page`、`page_size`、`sort`；后端使用白名单校验，限制窗口与分页上限。返回版本化响应、`generated_at`、`metrics_data_until`、`last_probe_completed_at`、覆盖信息及可空指标。

分组行拥有稳定 `public_id`，样本拥有不暴露内部渠道 ID 的公开标识。顶层摘要根据筛选范围计算但不受当前分页限制；缩略图与指标查询不会触发检测。

后端检查状态页开关和导航模块访问控制，并在服务层过滤公开范围。公开缓存与管理员查询缓存分离，缓存键包含模型、窗口、筛选条件和公开配置版本。

### 管理员接口

统一前缀建议 `/api/quality-detection`：

- `GET/PUT /settings`：读取与保存运行设置、公开范围；保存返回版本，冲突时要求重新加载。
- `GET /channels`、`PUT /channels/:id`：配置与检查渠道检测能力。
- `GET/POST /prompts`、`POST /prompts/:id/versions`：预设与新版本；归档使用显式变更接口。
- `POST /batches`：手动创建批次，返回 `202` 与批次标识；重复幂等提交返回已有结果，运行冲突返回 `409`。
- `GET /batches`、`GET /batches/:id`：分页历史、进度与摘要。
- `POST /batches/:id/cancel`：持久化取消请求；重复取消幂等。
- `GET /runs/:id`、`GET /runs/:id/output`：样本元数据与受控纯文本/附件输出。
- `POST /runs/:id/baseline`、`POST /runs/:id/review`：基线与人工复核，写审计记录。

所有变更接口使用管理员认证、现有敏感操作限流及适用的来源校验；模型提示词、渠道凭据与错误上下文不回传公共接口。

前端使用 React Query 读取与更新数据：运行时约 2 秒轮询，完成后停止详情轮询；公共页面约 30 秒刷新已保存结果，页面不可见时暂停。上述刷新频率与真正模型检测间隔是两个独立概念。

## 14. Uptime Kuma 替换与集成改动

### 后端接入点

- `router/api-router.go`：新增公共状态和管理接口；旧 `/api/uptime/status` 停止外呼，按弃用策略返回明确的已停用响应。
- `controller/misc.go`：发布新的状态页能力字段，前端不再依赖 `uptime_kuma_enabled`。
- `service/system_task.go`、任务注册位置与 `main.go`：注册质量检测与执行器，复用主节点执行和数据库租约。
- 新增控制器、服务、模型与设置域；在 `model/main.go` 等迁移入口注册模型。
- 原有渠道连通性测试保留；质量检测不接管自动禁用、恢复和渠道路由控制。
- `pkg/perf_metrics` / `model/perf_metric.go`：补充按公开分组批量读取计数的查询，不破坏模型广场原有响应契约。

### 前端接入点

- `web/src/features/status/`：替换数据源与页面结构；按职责拆分筛选、分组列表、详情、样本预览。
- 新增 `web/src/features/quality-detection/` 与 `_authenticated` 下对应管理路由。
- `use-sidebar-data.ts`、`use-sidebar-config.ts` 及侧边栏设置：增加“降智检测”入口和模块配置，不绕过角色过滤。
- `use-top-nav-links.ts`、`use-status-data.ts`、状态返回类型：解除对 Kuma 开关的依赖。
- 控制台 `UptimePanel` 改用原生分组摘要；避免旧概览继续请求 Kuma。
- 系统设置中停用 Kuma 配置入口，改为状态页发布配置入口或引导至“降智检测”。
- OpenAPI 文档、七种前端语言、后台错误文案和相关测试一起更新。翻译键遵循项目现有英文源字符串规范，实施时先加载项目 i18n 技能。

### 迁移原则

- 第一版上线即停止状态页和概览对 Kuma 的运行时依赖，不在失败时悄悄回退请求 Kuma。
- Kuma 分类与真实渠道分组没有可信的一一映射，不自动把旧分类转换为新公开分组，也不导入它的成功率作为检测历史。
- 旧设置值和已有兼容迁移保留用于回滚，不破坏性删除。公开分组需要管理员明确选择；首次上线可以先配置后启用公开页。
- 前后端协调发布；旧接口的具体弃用窗口在实施发布说明中确定，但旧接口不会继续触发 Kuma 外呼。
- 所有 new-api、QuantumNous 标识、版权与归属信息保持不变。

## 15. 测试与验收

### 后端关键回归

1. 一个渠道属于三个分组时，一轮只调用一次模型，三个分组引用同一结果与产物。
2. 两个分组有部分相同渠道时，执行数量等于渠道并集数量；同一组多个模型能力记录不增加调用次数。
3. 两个主节点、重复手动提交与定时/手动碰撞时，不产生重复批次或重复渠道执行。
4. 渠道禁用、模型不可用、参数覆盖冲突、配置中途修改、无可用密钥均得到明确分类。
5. 页面离开不取消任务；取消、失锁和重启不会自动重发生成，也不会被旧执行者写成成功。
6. 预算不足、并发预留、跨日完成、超大 token 参数和未知 usage 不绕过限制、不误扣钱包。
7. 流中断、超时、输出上限、HTTP 成功但正文无效能被正确区分；截图失败不改变上游成功事实。
8. 分组比例按计数加权；全站检测按唯一记录去重；无样本为 null，不能生成伪造历史。
9. 私有组、私有渠道、原始错误、输出源码不会进入公共响应；撤销公开后无法继续读取受控截图。
10. 三种数据库上验证迁移、唯一约束、任务领取、预算预留、清理和重启恢复。
11. 质量检测成功、失败或取消时，不通过共享测试回调改变生产渠道启停状态、路由权重或既有失败/冷却状态；原有连通性测试的状态更新契约不受影响。

### 前端与渲染回归

- 验证桌面/手机布局、长分组名、零/单/多样本、筛选后分页与摘要一致性。
- 覆盖加载、局部刷新失败、过期、未配置、全部失败、预算暂停与渲染不可用。
- 用户切换模型/时间窗口不能触发模型任务；刷新只读取已有结果。
- 预览抽屉焦点、Escape 关闭、排序可访问状态、减少动态效果和语言切换均有回归测试。
- HTML 输出始终作为不可信内容；验证隔离渲染的网络禁用、资源上限和公开页仅加载静态图片。
- 前端测试放在模块专属 `__tests__/`；后端测试使用 testify，优先确定性的行为与契约断言。

实施后至少运行受影响测试、`bun run typecheck`、涉及文件的 lint/format 检查和生产构建；数据库兼容与渲染隔离测试单独验收。本轮实际检查结果和待验收项记录在 [实施与部署说明](quality-detection-rollout.md)，未通过的检查不作为完成项。

### 最终验收场景

配置渠道 A 属于“标准、会员”，渠道 B 属于“会员”，均启用一个检测模型与一个预设。手动运行一轮：

- 实际发生两次模型生成，不是三次。
- “标准”展示 A 的结果；“会员”展示 A 与 B，A 的截图地址与检测记录完全相同。
- 全站检测数量是 2；“会员”覆盖是 2/2，不能把 A 重复计数。
- 刷新、切换分组、打开详情、查看历史不会增加上游调用。
- 停止渲染服务后仍保留生成记录，界面说明缺少截图，不标记模型降智。
- 停用或撤回分组发布后，公共接口与截图读取同步失效。

## 16. 实施顺序与待确认取舍

建议分四步交付，每一步都可独立验收：

1. **检测核心**：持久化模型、任务去重、预算、单次模型执行、终态与取消；用可控上游测试验证一次调用约束。
2. **后台工作台**：设置、渠道配置、预设、历史、基线与人工复核；先让真实样本可追踪。
3. **渲染与原生状态页**：隔离截图、分组聚合、公开权限、Arc 风格列表与详情。
4. **整体切换**：导航、概览、设置、旧接口停用、兼容检查与跨数据库验收。

已确认以下默认决策：

- 每渠道每轮一个模型、一个提示词；不是每组、每模型全量检测。
- 第一版采用规则证据与人工比较，不额外调用评审模型。
- 使用现有系统任务框架，不新增外部任务队列；截图采用独立受限渲染组件。
- 公共页以分组为主行，渠道结果放在详情，公开范围由管理员主动发布。
- 第一版业务指标按已落库时间桶展示，后续再扩展跨实例实时指标与 P95。
